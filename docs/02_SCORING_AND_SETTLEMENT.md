# 数学规则与结算实现

## 术语

| 名称 | 含义 | 精度 |
|---|---|---|
| 分配点数 allocation | 评分者给一张 target 的点数 | 非负整数，单份合计 100 |
| 实时瘤度分 liveScore | 最新有效方案给该 target 的平均分 | 四舍五入 1 位，用此值排名 |
| 当日奖励 dailyReward | 当日结算按占位平分得到的积分 | 当日先四舍五入 1 位 |
| 霸榜瘤值 dominance | 该 target 各日奖励之和 | 累计已取 1 位的小数，显示 1 位 |
| 当前方案 currentAllocation | 一个评分者最新有效提交 | 恰好一份参与当前计分 |
| 版本 allocationVersion | 某次有效提交的历史记录 | 保留时间，以便截止时点重建 |
| 日结算 dailySettlement | 固定日期的榜单/奖励快照 | 一天只能发一次 |

## 平均分及名次

设 C 是截止时点已经至少成功提交过一份方案的评分者集合。对每个人只取截止时点前最后有效版本。

```text
N = |C|
total(target) = Σ allocation(participant, target)，缺省项为 0
liveScore(target) = N == 0 ? 0.0 : round1(total(target) / N)
rank(target) = 1 + 分数严格大于 liveScore(target) 的 target 数量
```

隐藏和公开方案同样计分。修改自己的方案不使 N 增加。尚未填写新头像的旧方案，仍作为它的 0 分评分者。

参考代码：`core.mjs` 中 `round1`、`board`、`rank`。原型同分时按 target.id 稳定排序，但**顺序不同不改变并列名次**。

## 并列奖励统一公式

```text
prize(k) = k=1 ? 6 : k=2 ? 3 : k=3 ? 1 : 0
并列组人数 m、起始名次 r
pool = Σ prize(k)，k 从 r 到 r+m-1
dailyReward = liveScore == 0 ? 0.0 : round1(pool / m)
```

不要按“有几个并列第一就每人 6 点”发奖，也不要硬编码仅支持两人并列。

| 场景 | 每人奖励 | 后续名次 |
|---|---|---|
| 无并列 | 6.0、3.0、1.0 | 第四起 0 |
| 两人并列第一 | 各 (6+3)/2 = 4.5 | 下一名为第三，加 1.0 |
| 两人并列第二 | 第一加 6.0；并列者各 (3+1)/2 = 2.0 | 下一名为第四 |
| 三人并列第一 | 各 round1(10/3) = 3.3 | 下一名为第四 |
| 两人并列第三 | 各 (1+0)/2 = 0.5 | 下一名为第五 |
| 四人并列第一 | 各 round1(10/4) = 2.5 | 下一名为第五 |
| 一人 100 分，其余 0 分 | 只有第一得 6.0，其余 0 | 0 分即使处于第二并列组也不发奖 |
| 所有 target 都 0 分 | 全部 0 奖励 | 排行榜仍全员显示、同分并列 |

**不要求当日奖励总和精确为 10.0**：例如三人并列第一，各 3.3 合计 9.9。用户否定“保留更高精度到累计最后再取舍”的建议，选择每日及实时均为 1 位。不要做尾差补偿或把三天 3.3 自动改成 10.0。

建议小程序服务端用整数“十分之一点”存储 liveScore/dailyReward/dominance，避免 0.1 连续累加的二进制浮点误差；这是实现建议，不改变按日先舍入的业务语义。

## 23:59 的时间语义

- 用户确认到“每天 23:59”；网页把它落实为 `YYYY-MM-DDT23:59:00+08:00`，不是 23:59:59 或次日 00:00。
- 截止时点 `t`：取 `version.time <= t` 的每人最后有效版本；`target.created <= t` 的 target 才属于该日。
- 截止之后收到的提交影响实时榜和以后日期，不进入已过截止日。
- 始终由服务端赋时间；不要用用户手机时间决定结算归属。可在云端存 UTC 时间戳，但日期键必须按 Asia/Shanghai 得到。
- 如果实际云定时器使用 UTC，23:59 北京时间等价于 15:59 UTC；定时表达式格式和平台时区必须查对应供应商官方文档，不能直接套用某个未经验证的 cron 字符串。

## 快照内容

至少保存：日期、业务截止时间、当日参与人数、各前三奖励名次 target ID/头像引用、名次、当日 liveScore、当日奖励。累计可以从这些固定日记录求和，也可事务性维护汇总。

并列组跨过第三名时，整个并列组都应出现在结果里。例如两人并列第三，历史必须记录两张头像和各自 0.5，不能仅保留列表的第三项。

网页 `awards` 当前返回所有 `rank <= 3` 的行，包括 0 分、0 奖励行。所有 target 为 0 时可能记录 13 行并列第一、奖励均 0。用户已确认 0 分全员上榜、不发奖，但没有单独指定“无提交日历史列表的空态”；可以沿用这个忠实快照表达，或在 UI 标明“当日无积分发放”，不要误称只有三个获奖头像。

## 幂等与补算

网页当前：

1. 数据含 `created`、全部 `versions`、`targets.created` 和 `days[YYYY-MM-DD]`。
2. 每秒扫描应结算日期；启动和读状态/写数据前也补算。
3. 已有 `days[date]` 直接跳过，不重复累计。
4. 缺少日期时，用该日 cutoff 重建当时的榜单，保存固定结果。
5. 总霸榜值是日记录奖励的求和。分配原值跨天一直有效。

云端迁移必须加强为**数据库唯一日期键 + 事务/幂等写入**。定时器重试、多实例并发、用户请求同时触发补算时，不能双倍发奖。

不要只存每人最新方案、然后用“重启时的当前榜单”补过去所有日期；那会把截止之后的修改错误写入历史。需要保留带服务端时间/版本顺序的记录或提供等价的时间点恢复能力。

旧网页不是分布式实现；在单 Node 进程内同步写临时文件再重命名，不能作为多实例云部署的锁和事务方案。
